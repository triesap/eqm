## Scope

DEV-009 allocates typed record-kind/reference distinctions and validated
already-defined references along the approved lifecycle:
`authority/candidate -> plan/campaign -> evidence/worker/runtime ->
frozen-input -> decision -> statement -> authorization -> deployment-receipt`.
Evidence binds a plan/candidate subject, not the future decision that includes
it; post-deployment observations feed a later evaluation. No storage or
publication is implied, and no timestamp or directory order substitutes for a
reference.

## Representation

`crates/eqm_domain/src/record.rs` (new) exports:

- `RecordKind` — the twelve approved lifecycle kinds in dependency order. Each
  kind has an exact canonical token and a lifecycle row; `evidence`, `worker`
  and `runtime` share one row because the lifecycle lists them together.
- `RecordRef` — a typed directed reference to one record kind plus one validated
  symbolic `RecordId`.
- `RecordDescriptor` — a record with private fields, constructible only through
  `RecordDescriptor::new`, which rejects a self-reference and a repeated
  reference. Raw deserialization cannot promote data into a validated record.
- `ValidatedRecords` / `validate_records` — the checked registry. It rejects:
  - duplicate `(kind, id)` records (`DuplicateRecord`);
  - references to records absent from the supplied registry
    (`MissingReference`);
  - references to a later lifecycle row, such as evidence to its future
    decision (`FutureReference`);
  - directed cycles, including same-row cycles (`CyclicReference`).
- `RecordId` was added to the existing validated identifier family; no new digest
  domain or wire representation is invented.

The acyclic direction check is row-based; cycle detection is an iterative
depth-first traversal with explicit colors, so a same-row cycle is still
rejected even when every edge is non-future.

The step is domain-only. No protocol wire kind or schema is introduced, because
DEV-009 freezes no wire carrier for these records and this step implies no
storage or publication. A later owning step must add any wire form together with
its dispatch and parity controls.

## Corrective checkpoint S026-R1 — repeated acyclic evaluations (DEV-011 RF42)

**Scope:** DEV-011 S026-R1 / RF42. **Baseline HEAD:**
`ac20f545127a7eb1daec2754eafbb819d40e9c7d` (S025-R2).
**Resulting commit SHA:** recorded in the next ledger update (no self-reference).
**Commit subject:** `fix: allow historical deployment inputs in acyclic record histories`.

RF42: the global lifecycle-row check rejected an already-defined deployment
receipt consumed by a later runtime/frozen input, and the registry did not
represent caller-declared creation order, so it could not distinguish an earlier
definition from a later same-kind record. `references()` also promised canonical
order but stored supplied order.

### Representation

`crates/eqm_domain/src/record.rs`:

- `validate_records` treats the supplied `Vec<RecordDescriptor>` as the explicit
  **ordered definition history**. A reference must resolve to a definition at an
  earlier index; the history is never sorted and the supplied order is preserved
  in the checked result.
- The lifecycle-direction check is retained with exactly two historical
  exceptions: `Runtime -> DeploymentReceipt` and
  `FrozenInput -> DeploymentReceipt` may reference an earlier-defined receipt.
  `Decision -> DeploymentReceipt`, `Evidence -> Decision` and every other
  later-row reference remain forbidden.
- Known-ID, duplicate-record, self-reference, missing/wrong-kind and
  directed-cycle checks are retained. The cycle walk stays iterative and bounded
  by supplied input; a same-kind or readiness/deployment cycle reports
  `CyclicReference`, and a forward definition reports `FutureReference`.
- `RecordDescriptor::new` stores `references` sorted by their complete typed
  `(kind, id)` identity and rejects duplicates, so `references()` is canonical
  and permuting the supplied member order is equivalent.

### Tests added and updated

- `historical_deployment_inputs_validate_after_an_initial_lifecycle`: full
  initial lifecycle then receipt → later runtime → later frozen input → later
  decision validates.
- `same_kind_forward_definition_rejects`, `future_receipt_rejects`,
  `future_reference_rejects`, `initial_readiness_on_a_future_deployment_rejects`
  and `evidence_to_decision_remains_forbidden` reject with `FutureReference`.
- `cyclic_history_rejects` and `initial_readiness_deployment_cycle_rejects`
  reject with `CyclicReference`.
- `missing_reference_rejects`, `wrong_kind_reference_rejects`,
  `self_reference_rejects`, `duplicate_record_and_reference_reject` retain the
  existing controls.
- `reordered_definitions_into_forward_references_reject` proves the same records
  reject once the referenced definition is moved later.
- `permuted_reference_member_supply_is_equivalent` and
  `references_are_stored_in_canonical_complete_typed_order` prove canonical
  order.

No new epoch, product identifier, timestamp heuristic, digest domain, storage,
wire carrier or trust authority is created by this domain check.
